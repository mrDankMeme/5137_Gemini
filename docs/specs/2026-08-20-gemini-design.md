## 4. Архитектура

Clean Architecture + MVVM, зависимости направлены внутрь — как требует платформа.

```
Application/      GeminiApp, AppCompositionRoot  — единственное место сборки зависимостей
Core/
  DesignSystem/   AppColor, AppFont, компоненты
  Configuration/  AppConfiguration + отдельный файл временных значений
  Networking/     клиент, DTO, протоколы репозиториев
Features/         Splash, Onboarding, Paywall, Home, Chat, Photo, Menu,
                  Library, History, Settings — каждая со своей ViewModel
```

Модули платформы подключаются в порядке `BroadCore → BroadMonetization → BroadUIFlows`
через `Assembler` Swinject. Берём:

- `BroadCore` — запуск, кеш, offline, timeout/retry, `LoadableState`, логирование;
- `BroadMonetization` — Adapty, StoreKit, entitlement, токены, RU Billing;
- `BroadUIFlows` — маршрут `splash → onboarding → paywall → проверка доступа → main`,
  готовый `BroadActionButton`, special offer, RU Billing UI;
- `BroadExtensions` — hex-цвета, клавиатура, свайп назад.

Маршрут приложения ровно тот, что требует платформа:
запуск → onboarding → paywall → **новая** проверка доступа → основной экран.

## 5. Правила, которые нельзя нарушить

Из `AGENTS.md` и README платформы:

- ATT запрашивается **только после появления первого слайда onboarding**, никогда в loader.
- Rate Us в приложении есть, но **внутри onboarding запрещён**.
- Продукты Adapty показываем **все и в том порядке**, в каком пришли; UI обязан пережить 0, 1 и дубликаты.
- Покупка и восстановление **не открывают premium** до подтверждённой проверки entitlement.
- Offline и timeout **не превращаются** в inactive или success — результат остаётся pending.
- Любая кнопка к backend/SDK синхронно ставит `isInFlight = true` **до** `Task` и первого `await`.
- Очистка Keychain — только Debug, только по подтверждению, только свои service.
- Adapty: `nottrial` слитно, paywalls `main`/`tokens`/`special_offer`,
  placements `onboarding`, `pro_icon`, `settings`, `main`, `CTR`, `special_offer`,
  обязательный Remote Config `{"ru_pay": false, "auto_revenue_view": false, "special_offer": false}`.
- RU Billing включается только при свежем `ru_pay = true` **и** (регион РФ **или** первый язык русский).

## 11. Что придётся дописать, когда придут бэкенд и Adapty

Слои разделены правильно, и **вёрстка переживёт подключение почти без правок**.
Но заявление «замена репозиториев в одном месте» — полуправда: контракты писались
до спецификации API. Оценка работы — 12–17 человеко-дней при полной спеке.

### Чат: контракт не тот

Реальная генерация в reference трёхшаговая: `POST /api/generations/openai/conversation`
→ `POST /api/generations/openai/response` (возвращает **jobId**, не текст)
→ `GET /api/generations/{jobId}` в цикле до `finished`, это минуты.
Наш `send(...) async throws -> ChatMessage` — один round-trip. Дописать:

- `conversationID` как сущность и создание разговора;
- двухфазную отправку: `startGeneration -> JobID` и `poll(jobID)`;
- частичный результат (`partial_result`) — иначе пузырь пустой две-три минуты;
- курсорную пагинацию истории (`limit`/`after`, `order`) вместо `loadMessages(chatID:)`;
- серверные id сообщений вместо локальных `UUID`;
- отдельные ручки `/api/generations/image` и `/video` с multipart;
- авторизацию: `POST /api/users` → `/api/users/authorize` → Bearer;
- классификацию ошибок вместо четырёх доменных случаев, включая **409
  «разговор привязан к другой модели»** — этот сценарий требует создать новый
  разговор и переиграть историю.

### Монетизация: за протоколами не прячется

`PaywallRepositoryProtocol` отдаёт `PaywallPlan` с готовыми строками цен,
а Adapty даёт `MonetizationProduct` с `Money`, периодом и `ProductPresentationID`.
Это не «другая реализация того же протокола»: платформа приносит собственный слой —
`LoadPaywallUseCase`, `SelectProductUseCase`, `PaywallViewModel`, `EntitlementEngine`,
`MonetizationOperationGate`, менеджеры покупок. Подключать надо его, а `PaywallPlan`
заменить на `MonetizationProduct`, сохранив вёрстку.

### Что сломается молча, если не сделать

| Риск | Почему |
|---|---|
| Двойное списание | Генерация живёт на сервере минутами; один блип сети помечает ответ упавшим, пользователь жмёт повтор и платит второй раз |
| Потерянная оплаченная генерация | `stop()` отменяет только локальную задачу; job на сервере досчитается, результат исчезнет |
| Покупка без gate | Двойной тап = два Apple sheet'а; убийство приложения между оплатой и начислением = деньги без токенов |
| Hard-пейвол становится soft | Сбой Adapty даёт пустой каталог, и стартовый пейвол пролистывается без единой ошибки в UI |
| Дробный баланс | Сервер отдаёт `Double`; 0.5 токена округлилось бы в «токенов нет» |

Часть уже закрыта: баланс переведён на `Decimal`, каталог продуктов грузится один раз,
выбор продукта сбрасывается при смене каталога, записи откатываются при отказе,
параметры генерации отделены от подписей («5 sec» — подпись, на сервер уходит `5`).

### Механизмы платформы, которые ещё не подключены

`LoadableState` и `BroadLoadableView` (у экранов нет ни одного состояния загрузки
и ошибки), `AppError` с классификацией сбоев, `TimeoutPolicy`/`RetryPolicy`,
кеш-репозитории, `AdaptyPlacementRegistry`, весь `BroadMonetization`,
`BroadPaymentMethodSheet` для RU Billing, аналитика.

### Порядок работ

1. **Контракты и модель ошибок** — иначе остальное придётся переписывать дважды.
2. **Транспорт чата и генераций** — авторизация, polling, устойчивость к обрывам,
   восстановление незавершённых job'ов, реальные вложения.
3. **Монетизация** — сборка `BroadMonetizationAssembly`, покупки, токены, entitlement.
4. **Релизный минимум** — письмо в поддержку, Usedesk, Debug-экран, локализация,
   боевые значения вместо `DevelopmentConfiguration`.
